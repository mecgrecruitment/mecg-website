# Screening review continuity: interface verification

The screening review form now consumes the revision-safe SQL contract documented in [screening-draft-write-revisions.md](./screening-draft-write-revisions.md). This receipt covers the separate parser, API and local browser checks. All browser data was fictional and every screening API request was intercepted locally; no hosted profile, applicant, review or provider record was created or changed.

The gated route `/apply/test-harness/screening` renders the actual `ScreeningReviewForm` and `ScreeningReadingDesk` inside the `workspace-stack` full-width, `min-w-0` container. Both `PLAYWRIGHT_APPLICATION_HARNESS=1` and `E2E_LOCAL_HTTP=1` are required; the default route calls `notFound()` without those flags. The synthetic reader/scoring guide exercises the production desktop split pane and mobile reading/scoring tabs.

## Verified behavior

The focused Node suite passed **38 tests** across the screening draft parser/confirmation helper, private backup helper and both API routes. It checks explicit nullable revisions, missing revision refusal, malformed nonempty content failing closed, hidden old-rubric rows retaining their revision, bound saved/conflict/action receipts, exact saved observations with criterion-order independence, finite scores in the canonical 0–100 range, required notes for ratings 1 and 5, optional rating-2 notes, RPC argument forwarding, wrong assignment/mutation receipts, old scalar/void receipt refusal, strict external evidence/recommendation/recusal input types, and convenience next-link failure preserving a successful final submission.

The main browser matrix passed **100 checks**: 20 journeys in each of desktop Chromium, mobile Chromium, Firefox, desktop WebKit and mobile WebKit. After independent boundary review identified that a structurally valid receipt could contain different observations, the root implementation added semantic payload equality to the API and browser save guards. The affected follow-up passed **30 checks** across all five projects: exact mismatched-content receipt handling, the four lost/malformed submit/recuse cases and the final latest-draft wait. Two additional mobile conflict/export capture checks passed after resetting the screenshot scroll position. These are scoped runs and include repeated checks, rather than 132 different features. The final spec now contains 25 distinct journeys after the reading-desk follow-up below.

The browser journeys establish:

- A pending earlier save serializes newer edits. Unknown transport responses and stalled JSON bodies preserve the request and replay it exactly before newer observations use the confirmed revision.
- Conflicts preserve both private copies, expose downloads containing the correct copy and assignment, focus the comparison heading, and let a reviewer explicitly keep this page or use the server copy. Choosing either returns focus to the first scoring criterion. Old-rubric null content still protects replacement with its stored revision.
- Blocked and quota-limited session storage produce truthful backup warnings and retain a private download path. A valid session copy recovers after reload. Failed initial revision loading allows private scoring and recusal while preventing save/final submission; in-page retry retains memory-only edits and compares an existing server copy before any write.
- Final submission waits for an earlier incomplete draft save, drains the newer complete review under that revision and forwards the latest confirmed revision. A final CAS conflict opens the same explicit comparison without navigation.
- Lost or malformed submit and recuse results preserve observations and the existing private session backup, focus authoritative queue/reload recovery, disable consequential actions and avoid automatic replay or navigation. A definite replacement-coverage refusal retains data and enables another deliberate action.
- Full save-error feedback arriving between native pointer down/up leaves the rating hit area in place and lets the choice complete. Rating hit areas remain at least 44 CSS pixels high; measured label coordinates changed by at most one pixel. Conflict and feedback checks found no horizontal document overflow in the tested desktop/mobile viewports.

## Reading-desk recovery and keyboard follow-up

A later source review found that an initial local/server conflict could try to focus a heading while the mobile scorer was hidden behind the default Read tab. The root implementation added a view context that reveals Score once for a new conflict or unknown final action, then focuses the now-visible recovery element. A deliberate later return to Read remains usable. The reading desk also gained stable tab/panel associations, roving tab stops, ArrowLeft/ArrowRight and Home/End activation, and `min-w-0` panels.

The focused follow-up passed **50 browser checks** across the same five projects. Four new journeys per project exercised a 390-pixel viewport: a gated initial GET with different seeded local/server copies while Read starts selected; native keyboard navigation and tab/panel ID associations without an implicit save; a pending draft conflict arriving after returning to Read; and an unknown final action arriving after returning to Read. Each recovery journey verifies that Score becomes selected and the visible comparison heading or unknown-action alert receives focus. Each then deliberately selects Read and checks it remains selected and usable. The remaining 30 checks repeated both conflict/export choices and all four lost/malformed submit/recuse cases. There were no test failures or production changes by the verification agent in this phase. TypeScript and changed-test lint passed again.

`reading-desk-followup.log`, `reading-desk-types.log` and `reading-desk-lint.log` record that pass. The seeded initial-conflict proof is `initial-recovery-mobile-webkit.png`. The updated input manifest includes the exact reading-desk source and form source along with the new browser cases; the prior input manifest is retained separately.

## Evidence and limits

Raw results, earlier fixture/launcher failures, traces, input SHA-256 hashes and mobile screenshots are in [evidence/screening-ui-revisions](./evidence/screening-ui-revisions/). `browser-final.log` records the 100-check matrix, `receipt-followup.log` the 30 affected follow-ups, and `capture.log` the two recaptures. `node-tests.log`, `types.log` and `lint.log` record the focused Node, TypeScript and changed-file lint checks. TypeScript and lint passed.

The first host launch encountered an existing Next dev server lock, then missing host Chromium binaries. The established supported runner was used instead: `mcr.microsoft.com/playwright:v1.64.1-noble`, with host networking, the repository mounted at `/work`, `PLAYWRIGHT_PORT=3000`, `PLAYWRIGHT_CROSS_BROWSER=1` and at most two browser workers. Tests reused the already-running local gated Next server; no existing process was stopped. Host browser-launch failures are infrastructure failures, not product failures. The first actual browser run exposed ambiguous test locators and a StrictMode double-GET outage fixture; those test-only issues were corrected and their raw log retained.

The mobile comparison screenshots were inspected for copy/action visibility and overflow. Full-page capture required resetting the scroll position after download focus so the sticky mobile tabs appeared in their expected place. The Next development indicator remains visible. The screenshots establish local rendering in the synthetic harness, not production data behavior, real-device or assistive-technology acceptance, full accessibility conformance, or deployment readiness. The separately verified SQL receipt establishes database CAS, authorization and real connection races; these browser mocks do not replace that evidence.
