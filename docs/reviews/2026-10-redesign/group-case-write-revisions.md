# Revision-safe Group Case writes

The Group Case browser write path now uses `rate_group_case_applicant_v2` with a nullable expected revision and required mutation UUID. A successful save returns `kind: saved`, a new revision, the mutation ID, and the existing canonical observation receipt. A stale revision returns `kind: conflict` and the caller's current own observation snapshot. `group_case_roster_v2` retains the guarded roster and adds an explicit nullable revision to every applicant.

`20261016202000_group_case_write_revisions.sql` creates private, RLS-enabled state keyed by round, applicant and evaluator. Transaction-level advisory serialization covers the first save, before a state row exists. The state retains only the current revision, last mutation, canonical JSON request fingerprint and confirmed receipt. An identical current mutation confirms the exact committed result without reapplying it. Reusing the current mutation with different input fails. Retrying an older exact request after a newer revision returns a conflict; it cannot restore old scores or notes. This is a bounded current-mutation protocol, not an unbounded historical mutation ledger.

Mapped identity, current cycle authority, screening-reviewer exclusion, applicant participation/eligibility and declared conflict are checked before returning conflict or replay data. An exact already-committed current mutation can be confirmed after round closure or deadline because confirmation is read-only. Its snapshot is freshly projected from the caller's own latest nonvoid observation and current active rubric; changed quality or content returns a conflict instead of a stale confirmation. New mutations retain active-round, deadline and assignment lock checks and invoke the existing guarded rating function for all validation, calibration, scoring, evidence, eligibility and audit writes. The deadline is checked using the actual clock after serialization, so time spent waiting for another writer cannot extend a grading window.

The private snapshot helper mirrors the existing roster's own-observation projection without rebuilding the full cohort for each save. It exposes no new evaluator input at the public boundary. Revision state cascades when its round, application or evaluator is deleted. Authenticated and anonymous callers have no direct table access or snapshot-helper execute permission. Both v2 RPCs remain guarded security definers owned by postgres with an empty search path.

## Rollout

Authenticated execute on the old unconditional `rate_group_case_applicant` RPC is revoked to prevent a browser bypass around revisions. Trusted service-role execute remains. The consuming application must migrate to v2 with this migration; old browser clients receive permission denial rather than silently bypassing conflict protection. Generic written-evaluation draft writes are outside this change.

Three existing SQL suites now use a transaction-local compatibility adapter that reads the current own v2 roster revision and invokes v2 with a fresh mutation UUID. The adapter is security invoker, so the actual authenticated identity and all production guards remain exercised. It strips only the additive receipt fields for existing assertions. One old fixture probed a published round in another cycle without membership: its expected error changes from round-closed to forbidden because v2 reauthorizes before returning any replay or conflict data. No expected scoring or validity result changed.
