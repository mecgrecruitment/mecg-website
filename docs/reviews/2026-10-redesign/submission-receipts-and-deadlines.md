# Submission receipts and bounded operator acknowledgements

Later working-tree response to frozen V1 panel041–047. These fixes cannot alter those votes.

Final submission now consumes a bounded full JSON response and requires a nonempty bounded application ID before removing recovery. Missing/malformed successful receipts, transport loss, timeouts and ambiguous server failures reconcile against caller-scoped stored status for the exact cycle being submitted. A prior cycle's application cannot confirm the new form. Unknown outcomes retain answers and recovery. Autosave uses the same full-body deadline while preserving its exact mutation/revision retry contract.

The status API requires a cycle ID. Its existing caller-owned status RPC is checked against that application's cycle through the caller-scoped client before returning a confirmation. Missing cycle preconditions fail closed, including old clients; coordinate application rollout and reload old forms. This adds no service-role access or database policy. The dashboard acknowledgement now carries the application ID in the URL and independently verifies that it belongs to the loaded owned dashboard and has stored submitted state. A forged flag or a draft does not render an application-received banner. The submit API also refuses empty IDs and does not schedule a receipt for them.

Batch release preflight/write and incident-resolution waits now cover authorization, headers and the full response body with a15-second deadline. A release timeout/lost acknowledgement removes the old cohort confirmation, reports unknown outcome and requires a fresh server preflight. A committed-then-lost synthetic response proves that fresh review contains no already-released item and no second write occurs. Incident timeout gives an unconfirmed resolution with an explicit queue-check path. Actual applicant-visible release, email delivery and account remediation were not performed.

The operator-close implementation and its browser recovery follow-up are documented separately in [operator-close-ambiguity.md](operator-close-ambiguity.md). It distinguishes explicit rejection from unknown acknowledgement, checks authoritative status, and never treats ACTIVE alone as proof that an ambiguous transaction cannot still commit. A browser marker preserves unresolved state across same-tab reload when storage is available.

These are synthetic/intercepted local fixtures, not hosted acceptance. The final full-suite/build receipt will record its own actual terminal outcomes. No SQL behavior, production data, real emails or external accounts changed in this follow-up.
