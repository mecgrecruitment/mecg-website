# Contact and offer recovery — later than V1

Panel seats 055/057 identified delivery ambiguity and an outage mislabeled as excessive contact messages. The contact form now keeps a random UUID intent in memory for the canonical unchanged payload. Unchanged in-page retries reuse it; edited messages receive a new key; confirmed success clears it. The API validates the key, forwards it through the existing email adapter's `Idempotency-Key` header, and requires a nonempty provider receipt before reporting success. No contact content is persisted in browser storage.

This uses [Resend's documented idempotency contract](https://resend.com/docs/dashboard/emails/idempotency-keys), whose retention is **24 hours**. It is not a durable application ledger or a universal exactly-once guarantee. Reloading, another tab, editing, retention expiry or provider configuration changes can end the protection. Copy asks the user to retry unchanged to reuse the request and preserves the email alternative. A provider receipt acknowledges provider acceptance, not inbox arrival.

The endpoint now returns a distinct 503 for unavailable abuse protection, retaining fail-closed behavior. Actual quota exhaustion remains 429. Unknown email acknowledgement returns 502 with uncertainty guidance rather than asserting non-delivery. Old clients without the new intent fail closed with reload/copy guidance.

Panel seats 061/062 found that the applicant receipt overstated anonymity. It now explains that the written packet omits profile identifiers but assigned reviewers may see the identifying original resume. Seat 064's offer-deadline lookup issue is also corrected: an unavailable lookup shows an unknown response window, retry and Board contact actions. Pending response buttons wait for a successful lookup; already-recorded responses remain visible. It does not infer that an offer is open or expired from unavailable data.

The current Node suite has **699 passing assertions/tests**, including invalid contact keys, provider receipt requirements, limiter outage, precise applicant receipt disclosure, and stale future/expired deadline data accompanying a lookup error, malformed entry values and valid empty maps. The SQL RPC intentionally omits null deadlines; a missing key after a valid successful lookup retains that no-expiry meaning. TypeScript, lint and production build pass. The complete patched browser run passed400 checks across five configurations, including nine contact scenarios per configuration. A390px production contact capture has no horizontal overflow and retains the uncertain message with retry enabled. Exact run scopes and logs are recorded in the implementation receipt. No hosted email was sent and no live offer record changed.
