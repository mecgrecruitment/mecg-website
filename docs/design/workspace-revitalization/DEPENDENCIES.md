# Shared dependencies and build boundaries

Proposal only. IDs are shared by the feature inventory and atlas; they are not application code modules.

- **C1 — Shared presentation and focus.** Explicit private-workspace style scope, independent of sidebar presence; current tokens; readable reflow, 44px actions, keyboard/focus continuity and restrained announcements. Existing public/auth styling remains outside the migration unless intentionally reviewed.
- **C2 — Authorized role, task and cohort context.** Actual server capabilities, task eligibility, correct counts/units, preserved deep links and safe return paths. Unknown availability is not zero. A menu is not an authorization boundary.
- **C3 — Honest state and feature-specific recovery.** Domain-owned persistence, quality, editability, final locking, release and provider-send facts stay separate. Preserve existing revision/conflict/reconciliation safeguards. Ordinary confirmed work gains no new confirmation dialog. Investigate specific unsafe exits; a universal save/leave platform is not a prerequisite.
- **C4 — Explicit new contract work.** Separate the existing-data presentation increment from authoritative aggregation, capability/readback, revision/mutation or reconciliation work. These changes require endpoint/domain review and meaningful behavioral verification; local wording cannot implement them. They are not one combined mandatory release.
- **C5 — Policy/content owner decision where applicable.** Blind-resume content/access, mutable inline evidence versus immutable final submissions, corrections, feedback, accommodations, retention, membership activation, approval provenance and next-cycle handover. Existing rules stay enforced pending the appropriate decision. This dependency blocks the affected behavior/claim, not unrelated visual improvements.

Relative effort: S = localized presentation using existing facts; M = coordinated components/state or an existing-data journey; L = new contract/schema/integration or policy-dependent behavior. These are planning estimates, not dates. A mixed feature's presentation can often ship before its optional new contract.

## Acceptance slices

1. Fix established state/permission/recovery misrepresentation and record specific policy gates; prove shared style/focus roles on a representative route without a sidebar.
2. Complete one applicant, one reviewer and one operator handoff using existing contracts. Keep checks of exact cycle, authorized fields, pending/unknown results and final-action semantics in each slice.
